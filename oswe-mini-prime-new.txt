## Main findings & risks 🔧

1. **Local persistence is missing / inconsistent**
   - App.tsx imports `loadTodos` / `saveTodos` from storage.ts but **does not use them**. The app currently keeps todos only in memory (lost on reload), despite a storage module existing.
   - Risk: developer intent unclear (was persistence planned but not completed?), and users may expect local persistence.

2. **Type consistency and typing gaps**
   - storage.ts uses `unknown[]` and returns `any[]` — not typed to the `Todo` interface (defined in App.tsx), so typing safety is lost when integrating storage with state.
   - helpers.ts functions accept/return loose shapes (e.g., `{ priority: string }[]`) rather than the `Todo` type.
   - Risk: type mismatches or runtime errors when connecting storage or helpers to real `Todo` objects.

3. **State updates could be safer (race conditions)**
   - `setTodos([...todos, newTodo])` and other updates reference `todos` directly rather than the functional updater `setTodos(prev => ...)`. Concurrent updates (e.g., multiple quick adds) could cause stale-state bugs.
   - Suggestion: use functional updates to avoid races.

4. **Unused helpers & fields**
   - helpers.ts provides `formatDate`, `sortTodosByPriority`, and `getCompletedCount`, but none are used in the UI.
   - `Todo.createdAt` is set but never displayed (or used to sort).
   - Risk: dead code or incomplete features (e.g., priority-based sorting, date display).

5. **Mutating sort utility**
   - `sortTodosByPriority` calls `todos.sort(...)`, which mutates the input array. That can cause unexpected side-effects if callers expect a pure function.
   - Recommendation: return a new sorted array (e.g., `return [...todos].sort(...)`).

6. **Accessibility & UX considerations**
   - `Delete` provides no confirmation or undo and there’s no edit functionality.
   - Buttons lack ARIA labels or keyboard hints; filter controls are buttons (OK) but could include semantics (e.g., role="tablist" if intending tab-like behavior).
   - Consider showing counts (using `getCompletedCount`) or active task number.

7. **ID generation**
   - IDs are generated with `Date.now().toString()` — fine in many cases, but could collide in rare rapid adds. Consider `crypto.randomUUID()` or an explicit UUID generator if uniqueness matters.

8. **Error handling & edge cases**
   - `storage.saveTodos` / `loadTodos` log errors but don't surface them to the UI. Also, localStorage could be unavailable (private mode) — consider fallback strategy.
   - No validation beyond trimming the text (e.g., max length, prohibited characters).

9. **Testing & CI**
   - No tests or test dependencies are present. Adding unit tests for utilities and basic component/behavior would increase confidence for future changes.
